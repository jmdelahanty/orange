# Detect TensorRT Calibration Dataset

Date: 2026-05-20

Scope: define the Orange-side data set Palette should use when building or
evaluating a TensorRT INT8 engine for the single-fish detect model.

## Bottom Line

Yes: collect a representative set of Orange camera frames, including fish
examples from all production cameras, and give Palette that data as a specific
calibration and validation dataset for TensorRT engine creation.

This is not a model-training dataset. TensorRT INT8 calibration does not need
labels. It needs representative examples so TensorRT can choose activation
ranges and quantization scales that match production inference.

The dataset should not be fish-only. Production inference sees many no-fish and
background-heavy frames, and calibration should represent both positive and
negative scenes.

## Dataset Roles

Use two separate sets:

```text
calibration set:
  unlabeled representative frames or tensors
  used to build INT8 calibration scales/cache or Q/DQ quantization

validation set:
  held out from calibration
  labeled, inspected, or paired with trusted FP16 reference outputs
  used to compare FP16 vs INT8 detection behavior
```

Do not judge an INT8 engine by speed alone. A faster detector is only useful if
it preserves top-1 fish recall, box placement, score behavior, and downstream
crop safety.

## Orange Tensor Contract

Palette should calibrate against the same tensor distribution Orange feeds to
TensorRT, not against arbitrary RGB images.

Current mono-camera detection preprocessing is:

```text
source:
  live uint8 Mono8 camera frame

preprocess:
  resize with letterbox to 640x640
  padding value 114
  convert to FP32
  divide by 255.0
  replicate mono value into B, G, R planes
  layout NCHW, planar channel order BBB... GGG... RRR...

TensorRT input:
  tensor name: images
  shape: 1x3x640x640
  dtype: FP32 input buffer for the current Orange engine wrapper
```

For the current local four-camera A16 setup, include all four cameras:

```text
2010093
2010094
2010095
2010096
```

## What To Capture

Capture short, varied samples rather than one long homogeneous run.

Recommended coverage:

- fish present in normal positions
- fish near image edges
- fish at different apparent sizes and orientations
- partial occlusion or low-contrast fish
- motion blur from normal movement
- no-fish/background frames
- bubbles, debris, reflections, and ordinary dish texture
- bright, dim, and typical lighting/exposure settings
- examples from every camera that will use the engine

A practical first target is:

```text
calibration:
  100-300 selected frames per camera
  sampled across several short captures

validation:
  separate held-out frames
  enough positive fish examples to catch false negatives
  enough no-fish examples to catch false positives
```

More frames are useful only when they add visual coverage. Thousands of nearly
identical frames from one camera or one fish pose are weaker than a smaller,
balanced set.

## Preferred Representations

Best representation:

```text
exact post-Orange-preprocess tensors
  images, FP32, 1x3x640x640
  generated by the same preprocessing path used before YOLO enqueue
```

This is the cleanest TensorRT calibration input because the calibrator sees the
same tensor values the deployed Orange process would feed to the model.

Good representation:

```text
full-resolution uint8 mono/luma source frames
  plus an offline converter that exactly reproduces Orange preprocessing
```

This keeps the data compact and lets Palette regenerate tensors for future
input sizes or preprocessing versions.

Current practical Orange representation:

```text
pre_encoder_reference_capture output
  NV12 encoder-preprocess dump
  use only the luma plane as source-like mono input
  then run exact Orange YOLO preprocessing offline
```

Caveats for `pre_encoder_reference_capture`:

- It is not a YOLO tensor dump.
- It is not sensor-native camera raw.
- It captures prepared encoder input before NVENC.
- For current Mono8 full-frame recording, the luma plane can be used as a
  source-like mono frame only after validating metadata: dimensions, pitch,
  pixel format, no downsample, and normal camera settings.
- Do not feed raw NV12 bytes directly into TensorRT calibration.

Last-resort representation:

```text
decoded MP4 luma frames
```

This can be useful for rough experiments, but it includes encode/decode
artifacts and is less faithful to the live Orange TensorRT input.

## Manifest Requirements

Every dataset should include a machine-readable manifest. At minimum:

```text
dataset_id
dataset_role: calibration | validation
created_at
orange_repo
orange_commit
orange_preprocess_contract
model_family
camera_serial
source_run
source_artifact_path
recording_frame_id
camera_timestamp
width
height
pixel_format
pitch_or_stride
source_byte_offset, if packed into a raw dump
source_byte_size
fish_present: true | false | unknown
scene_tags
preprocess_input_size
preprocess_pad_value
preprocess_normalization
tensor_name
tensor_shape
tensor_dtype
checksum
```

For validation rows, include labels or reference outputs when available:

```text
fp16_num_dets
fp16_bbox
fp16_score
human_label_present
human_label_bbox, if labeled
```

## Palette Deliverables

For each candidate engine, Palette should return:

```text
model.onnx
model_fp16_a16.engine
model_int8_a16.engine
calibration.cache, if implicit calibration is used
calibration_manifest.json
validation_manifest.json
validation_report.json
engine_build_commands.txt
engine_metadata.json
```

`engine_metadata.json` should record:

- TensorRT version.
- CUDA version and driver version.
- GPU model and device ID used to build.
- ONNX SHA256.
- Engine SHA256.
- Input and output tensor names, shapes, and dtypes.
- Precision mode: FP16, implicit INT8, explicit Q/DQ INT8, or mixed.
- Builder flags and timing/optimization settings.
- Calibration dataset id.
- Validation dataset id.

## Acceptance Checks

Before Orange adopts an INT8 engine, compare it against the current FP16 A16
baseline on held-out validation data:

```text
detection/no-detection agreement
false negatives on fish-present frames
false positives on no-fish frames
bbox center drift
bbox width/height drift
score deltas
threshold crossings
crop safety margin impact
```

Then validate in Orange:

```text
standalone TensorRT latency on A16
headless four-camera PTP external-recorder run
GUI/session startup and recording run before production use
positive-detection crop/pose behavior with fish present
```

## Recommended First Workflow

1. Record several short runs with fish visible across cameras
   `2010093-2010096`.
2. Include background/no-fish clips from the same cameras and lighting.
3. Build a manifest that assigns each frame to calibration or validation.
4. Convert source frames through Orange-compatible preprocessing, or use a
   future exact YOLO tensor dump if available.
5. Have Palette build an INT8 candidate using the calibration split.
6. Compare INT8 vs FP16 on the held-out validation split.
7. Only then run Orange app-level latency and recording validation.
